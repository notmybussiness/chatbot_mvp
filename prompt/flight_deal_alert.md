# 항공권 특가 알림 프로그램 — 원샷 빌드 프롬프트

아래 `---` 사이의 내용을 통째로 복사해 Claude Code(또는 동급의 코딩 에이전트)에 붙여넣으면 됩니다.
`[[ ]]` 로 표시된 값만 본인 상황에 맞게 채우세요. 나머지는 기본값으로 동작합니다.

---

당신은 시니어 백엔드 엔지니어이자 웹 데이터 수집 전문가다. 아래 요구사항으로 **"항공권 특가 알림 프로그램"** 을 처음부터 끝까지 완성하라. 계획 → 구현 → 테스트 → 문서까지 한 번의 작업으로 끝내고, 중간에 되묻지 말고 아래 규칙과 기본값으로 판단하라. 단, 실제 외부 사이트 구조는 검증 없이 알 수 없으므로 **확인 안 된 것은 반드시 "검증 안 됨"으로 표시**하라. 확인 안 된 것을 확인된 것처럼 쓰는 것이 이 프로젝트의 가장 큰 실패다.

## 0. 내 설정값

- 관심 노선: [[ 예: ICN→NRT, ICN→BKK, ICN→CDG ]]
- 여행 기간 창: [[ 예: 출발 2026-11-01 ~ 2027-02-28, 체류 3~7일 ]]
- 인원/좌석: [[ 성인 1, 이코노미 ]]
- 예산 상한(절대 기준, 노선별): [[ 예: 일본 25만원, 동남아 35만원, 유럽 90만원 ]]
- 상대 기준: [[ 최근 30일 관측 중앙값 대비 20% 이상 저렴하면 특가 ]]
- 알림 채널: [[ Telegram (기본) | Slack | Discord | 이메일 ]]
- 확인 주기: [[ 특가/땡처리 페이지 30분, 검색형 소스 하루 2회 ]]
- 언어/스택: [[ Python 3.12 (기본, 권장) | Kotlin/Spring ]]
- 실행 환경: [[ 내 PC 상시 실행 | 라즈베리파이/홈서버 | 클라우드 ]]

## 1. 목표 한 줄

여러 소스에서 항공권 가격을 주기적으로 모아, **내 기준보다 싸게 나온 것만 골라 즉시 알림**을 보낸다.
핵심 가치는 두 가지다: **빨리 알아채는 것**, 그리고 **알림이 쓸모없어지지 않는 것**(스팸 금지).
알림이 하루 스무 개 오면 아무도 안 본다. 알림 하나하나가 "지금 봐야 하는 것"이어야 한다.

## 2. 데이터 소스 — 시작 전에 알아야 할 현실

아래는 조사된 사실이다. 이 전제를 무시한 설계는 배포 즉시 죽는다.

| 소스 | 실제 상태 | 접근 방식 |
|---|---|---|
| 스카이스캐너 | 공개 API 없음. Travel API는 파트너 심사 + 상업 계약 필요, 개인 승인 사실상 불가 | ❌ 직접 연동 불가. 어댑터 인터페이스만 만들고 **"미구현 — 파트너 키 필요"** 스텁으로 둔다 |
| 네이버 항공권 | 공개 API 없음. 프론트가 쓰는 내부 API(`flight-api.naver.com/.../searchFlights`, SSE 응답)를 역분석하는 방법뿐. **클라우드(AWS 등) IP 대역 차단** | ⚠️ 어댑터를 만들되 요청 본문·응답 필드명을 코드가 아닌 **설정/템플릿**으로 뺀다. 클라우드 배포 시 막힐 수 있음을 문서화 |
| 모두투어 공동구매 항공권 | API 없음. 목록 페이지 HTML | ⚠️ 목록 페이지 파싱 어댑터. CSS 선택자를 설정으로 뺀다 |
| 땡처리 항공권 (땡처리닷컴 등 여행사 땡처리 페이지) | API 없음. 목록 페이지 HTML | ⚠️ 동일 |
| Amadeus Self-Service | 2026-07-17 셀프서비스 포털 종료. 무료 티어 없음 | ❌ 쓰지 않는다 |
| Travelpayouts(Aviasales) Data API | 무료 가입, 캐시된 가격. 공식 경로 | ✅ 공식 소스로 하나 추가한다 (API 키는 내가 발급) |

원칙:

- 모든 소스는 **어댑터 하나 = 파일 하나**. 한 소스가 죽어도 다른 소스와 판정 로직은 영향 없어야 한다.
- **첫 구현은 Mock 어댑터**로 전체 파이프라인(수집 → 판정 → 알림)을 먼저 완성하고 테스트한다. 실제 어댑터는 그 다음이다.
- HTML/내부 API 어댑터는 선택자·엔드포인트·요청 본문을 **코드가 아닌 설정 파일**에 둔다. 사이트가 바뀌면 설정만 고치게.
- 각 어댑터는 `diagnose()` 를 제공한다: 실제로 보낸 요청과 받은 응답 원본을 그대로 반환해, 파싱이 깨졌을 때 추측 없이 원인을 볼 수 있게.
- **하지 말 것**: IP 로테이션/프록시 풀, 캡차 우회, 브라우저 지문 위조 등 차단 회피 장치. robots.txt 를 확인하고, 사이트당 요청 간격을 두고, 막히면 그냥 실패로 기록한다. 이건 개인 알림 도구지 크롤링 인프라가 아니다.

## 3. 아키텍처

```
[Source Adapters] → Offer(정규화) → [Price History Store] → [Deal Detector] → [Alert Dispatcher] → Telegram
   mock / travelpayouts / modetour / ddaeng / naver / (skyscanner: 스텁)
```

- **Offer 정규화 스키마**: `source, origin, destination, depart_date, return_date|null, price_krw, currency, airline, stops, url, fetched_at, raw_id(중복 판정용 소스 고유키), tags(특가/공동구매/땡처리 등 소스 라벨)`
- **저장**: SQLite 기본. 테이블 `offers`(관측 이력 전부), `alerts`(보낸 알림), `source_runs`(소스별 실행 결과·에러·건수)
- **판정과 알림은 저장된 데이터만 읽는다.** 외부 호출 없이 재실행·백테스트가 가능해야 한다.
- 판정 로직을 어댑터 안에 섞지 않는다. 어댑터는 "가져오기"만, 판정은 Detector만.

## 4. 특가 판정 규칙 (핵심)

아래 규칙 중 하나라도 해당하면 후보. **규칙별로 "왜 특가인지" 사유 문자열을 남긴다.**

1. **절대 기준**: `price ≤ 노선별 예산 상한`
2. **상대 기준**: `price ≤ 해당 노선의 최근 N일(기본 30) 관측 중앙값 × (1 − X%)` (기본 20%)
3. **역대 최저**: `price ≤ 해당 노선 관측 이래 최저가`
4. **신규 특가 등장**: 땡처리/공동구매/특가 태그가 붙은 항목이 **이전 실행에 없던 raw_id 로 새로 등장**
5. **급락**: 같은 raw_id 가 직전 관측 대비 Y% 이상 하락 (기본 15%)

**긴급도 점수(0~100)** 를 매겨 알림 제목에 반영한다. 가중 순서: 절대+상대 동시 충족 > 역대 최저 > 출발 임박한 땡처리 > 단일 규칙 충족.

**스팸 방지 — 알림이 쓸모없어지지 않게:**

- 같은 `(source, raw_id)` 는 **가격이 더 내려가지 않는 한 재알림 금지**
- 노선당 하루 최대 알림 수 제한 (기본 5)
- 관측 데이터가 N건 미만(기본 10)인 노선은 **상대 기준을 적용하지 않는다.** 기준선이 없는데 "싸다"고 하면 안 된다. 첫 며칠은 절대 기준과 태그 기준만 동작한다고 README 에 적어라.
- 조용한 시간대(기본 00~07시)는 모아서 아침에 한 번 요약으로 보낸다. 단 긴급도 90 이상은 즉시.

## 5. 알림

- 기본 **Telegram Bot** (무료, 즉시, 설정 5분). 토큰/챗ID 는 환경변수.
- 메시지 필수 항목: 긴급도, 노선, 날짜, 가격, **왜 특가인지(기준선 대비 얼마나 싼지)**, 항공사/경유, 소스, 링크
- 하루 1회 **요약 리포트**: 오늘 관측 건수, 알림 건수, 소스별 성공/실패 상태. 소스가 조용히 죽어 있는 걸 여기서 알아채야 한다.
- 발송 실패는 재시도 3회 후 로그. 프로그램은 죽지 않는다.

## 6. 스케줄링·운영

- 소스별 주기 설정 (특가 페이지는 짧게, 검색형은 길게). 소스 사이·요청 사이 지연 필수.
- 한 소스의 예외가 전체 실행을 죽이지 않는다. `source_runs` 에 성공/실패/건수/에러 기록.
- CLI 명령:
  - `run` — 1회 실행
  - `daemon` — 스케줄 상주
  - `diagnose <source>` — 해당 소스 요청/응답 원본 출력
  - `backtest` — 저장된 데이터로 판정만 재실행, 알림은 보내지 않음
  - `report` — 요약 리포트 즉시 출력
- 설정은 YAML 하나. 시크릿은 `.env`. **코드에 키 금지.**
- `--dry-run`: 알림 대신 stdout 출력.

## 7. 작업 순서 (이 순서대로, 각 단계 끝에 테스트 통과 확인)

1. 프로젝트 골격 + 설정 로딩 + SQLite 스키마
2. Offer 모델 + **Mock 어댑터** (결정적 가짜 가격, 날짜가 바뀌면 값이 변해서 등락 판정을 실제로 볼 수 있게)
3. **Deal Detector + 스팸 방지** — 여기에 단위 테스트를 가장 많이 쓴다: 규칙별 경계값, 데이터 부족 시 상대 기준 미적용, 재알림 억제, 급락, 일일 한도
4. Telegram Dispatcher (+ `--dry-run`)
5. 스케줄러 + CLI
6. 실제 어댑터를 **위험 낮은 순서**로: Travelpayouts → 모두투어 공동구매 → 땡처리 → 네이버. 각각 설정 기반, `diagnose()` 포함, 실패 격리. **실제 사이트를 호출해 보지 못했다면 파싱 로직은 "검증 안 됨"으로 표시**하고, 사용자가 어떤 절차로 확인·수정하는지 README 에 적어라.
7. Skyscanner 어댑터는 인터페이스 + 스텁만 (키 없음)
8. README: 설치, Telegram 봇 만드는 법, 설정값 설명, **소스별 한계와 고치는 절차**(선택자/템플릿 바꾸는 법), 검증된 것과 검증 안 된 것의 구분

## 8. 완료 기준

- Mock 만으로 `run --dry-run` 이 수집 → 판정 → 알림 메시지 출력까지 끝난다
- 판정 테스트가 4장의 5개 규칙과 스팸 방지 항목을 각각 커버한다
- 실제 어댑터 하나가 죽어도 나머지는 돌고, 그 실패가 요약 리포트에 보인다
- 사이트 구조가 바뀌었을 때 **코드 수정 없이 설정으로 대응 가능한 항목**이 README 에 적혀 있다
- 검증하지 못한 것이 README 와 코드 주석에 **"검증 안 됨"** 으로 명시되어 있다
